## Issue #130: state: priority rules for PTY agents, so an on-screen prompt outranks a stale hook report

A PTY agent's state in shed is whatever it last reported. When the agent shows a prompt that fires no hook, shed keeps saying `working` and the caller waits on a terminal that is waiting on a person.

## Today

1. `shed setup` wires Claude Code's hooks to `shed state`: `UserPromptSubmit` and `PostToolUse` report working, `PermissionRequest` blocked, `Stop` done, `StopFailure` error (`crates/shed-server/src/providers/claude.rs:10-20`).
2. The only fallback is silence: `idle` after `set_idle_after` (`crates/shed-core/src/terminal.rs:339-342`). A reported `working` is not overridden by anything on screen.
3. Screens with no hook behind them exist: a folder-trust question at start, a login prompt, a usage-limit banner, the program gone and a shell prompt in its place. For ACP agents shed already overrides state from text (`Limit::hit`, `auth_failures`); PTY agents have nothing like it.
4. agent-of-empires solves this with rules as data, `{id, state, priority, region, matcher}`, highest priority wins, and the hook report is one more rule (https://github.com/agent-of-empires/agent-of-empires/blob/main/docs/development/adding-agents.md).

The README's non-goal stands: no agent-brand detection in the core. This is the optional per-agent fallback it already allows, as data in the provider record.

## Scope

- A provider record gains `rules`: each has a state, a priority, a region (the last N screen lines) and a matcher (any of a list of substrings; no regex engine added).
- The agent's own report is a rule with a fixed priority. A screen rule above it wins while it matches and stops applying when it no longer does; one below it only applies when there is no report.
- Rules run on screen change, at most a few times a second, for terminals labelled with a known agent only. Other terminals pay nothing.
- `get` says where the state came from: `reported`, `rule:<id>` or `silence`.
- Ship rules only for prompts hooks miss. Collect the real screens first and keep them as golden files; do not write rules from memory.

Depends on #129 (providers as data) for where rules live. If that is declined, the rules go in the provider's Rust file.

## Acceptance criteria

- Commit 1 is the failing test: a terminal that reported `working` and then shows a golden trust-prompt screen reads `blocked`, with source `rule:<id>`.
- When the prompt leaves the screen the state returns to the report.
- A terminal with no agent label never runs a rule (asserted by a counter in the test).
- The drain bench (#80) is within its 10% limit with rules on.
- Each shipped rule has a golden screen and names the agent version it was captured from.
- Gates green, line cap holds.
