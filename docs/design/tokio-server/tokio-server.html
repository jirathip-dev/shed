shed-server on one tokio runtime

Design for jirathip-dev/shed#42 (step 3 of 3, after #41 and #40). Branch issue-42. For owner approval before any impl starts.

In short: connections, streams, terminal watchers and samplers become tasks on one multi-thread runtime (at most 4 workers). PTY reads stay on one plain thread per terminal. The ACP bridge loses its two glue threads. The two benches get faster through two changes. First, event fan-out moves to one shared log that subscriber tasks drain in batches: one push per event however many clients listen, instead of one channel send per client. Second, every stream writes a batch per wake instead of writing and flushing once per message. No new crate except tokio's socket2. Target: net ≤ 0 lines, because the repo is at 6,989 / 7,000.

Out of scope: the CLI side stays sync. That covers Client, attach, watch, relay and the machine stats fan-out over ssh. It is a short-lived process, no bench covers it, and the protocol is unchanged.

2. PTY and terminal reads, which block

A dedicated std thread per terminal, as today. read_loop is untouched. From that thread it bumps the terminal's watch and sends output to tokio unbounded mpsc subscribers, both of which are fine to call from sync code.

  • Not spawn_blocking: a terminal reads for hours. It would pin blocking-pool threads meant for short jobs, which share their cap with kill and df.
  • Not AsyncFd: it needs a non-blocking PTY master. Terminal::write (sync, called under the registry lock) would then see EAGAIN. kqueue on macOS PTY masters is unreliable. And it means rewriting core onto pty-process's async API, which costs more lines and wins nothing that tens of terminals need.

shed-core gets tokio with sync + time only (no runtime, no sockets). wait_until becomes async: a select! of changed() and sleep_until(deadline | idle | reap), which replaces the Condvar wait and wait_timeout loop. Core tests use #[tokio::test].

3. Runtime, threads, shutdown

  • Server: new_multi_thread(), worker_threads = min(cpus, 4), enable_all. Multi-thread because save() fsyncs under the lock and screen.watch diffs and serialises. On one worker, one slow call would stall every client. Capped at 4 because shed is a background daemon.
  • Bridge: current-thread, as in #40.
  • Shutdown: unchanged. Today the server has none: it is killed, its PTYs close and keep terminals come back on the next load. No signal handler is added. serve returns only on a bind or accept error.
  • Cancellation: when the read half reaches EOF, the stream task is aborted. When a stream ends, the socket is shut down. A watcher ends when its terminal exits. A wait whose client left runs to its own end (match, exit or timeout) as today, but as a task instead of a thread. spawn_blocking jobs run to completion.
  • Bridge exit: await the writer task so queued outputs land, then call shutdown_background(). Without it, the pending stdin read would hang the bridge at exit.

4. Where tokio wins, and how the benches show it

Fan-out. Events keeps one Arc<Mutex<Log>> of (Event, Line) and a watch::Sender<u64>. emit does one push and one notify, whatever N is. Each subscriber holds a cursor. When woken, it locks once, clones the matching lines after its cursor, and writes and flushes them as one batch. The log keeps ≥ 1,000 events for since and trims past the slowest live cursor. A slow client therefore keeps today's unbounded semantics, but with one shared copy instead of a queue per client.

ACP path (prompt → 1,000 updates → reply at a client):

  • the server's event stream does a write per batch, not 1,000 write+flush syscalls and cross-thread wakes;
  • in the bridge, session task → writer task stays in one runtime, so there is no futex wake or thread switch per batch;
  • a reserve lever if needed: emit notifications skip the per-request refresh() (a waitpid per running terminal). The watcher tasks already refresh on every change.

Bench rules for impl and rev. The CI jobs keep only the 10% floor. The amendment's gate is that the head's median of 5 beats the base's on both benches, and rev's PASS quotes both lines. At the head, tests/bench/fanout.rs changes only its API calls: subscribe returns a subscriber, and draining is take() after the burst. The workload stays identical: 5,000 events, n ∈ {1, 16, 64, 256}, best of 3, emit then drain, one thread. Rev diffs that file to check this. A report-only line in bench-fanout.sh covers many idle connections: 500 events clients and one state change, giving time-to-all and the server's thread count at base and head (500+ vs ≤ 4 + T). It shows the idle-connection win without gating on it.

Risk: ACP throughput varies 11–19 ms between runs here, a much wider spread than the fan-out bench. The Python agent and PTY rendering set a floor that tokio does not touch, so the margin over base on this bench may be thin. If the head’s median does not beat the base’s after commit 4, impl pulls the reserve lever and tunes the batch size before filing an ask.

6. Dependency

tokio is already in (=1.54.1, from #40). The workspace entry drops to no features, and each crate names what it uses. shed-server adds net (Unix sockets) and rt-multi-thread; the bridge adds io-std. shed-core takes only sync and time. The one new crate in Cargo.lock is socket2 (MIT OR Apache-2.0, already allowed by deny.toml), which tokio's net feature pulls in. dep-direction.sh is unaffected.

7. Open questions for the owner

  1. One PR with five green commits (recommended), or a sub-issue per commit? One PR keeps the amendment's “faster” gate on the whole step.
  2. Fallback trim if the cap is hit: may impl drop the berth→shed shims (Paths::move_old_dirs and $BERTH, about 30 lines, promised “for one release”)? Recommended yes, used only if needed. The alternative is a cap raise, which #41 ruled out.
  3. The CLI stays on threads and the sync Client (§1) (recommended), or should it move too? Moving it costs lines, and no bench measures it.
  4. Slow subscribers: keep today's unbounded retention, shared now (recommended), or cap the log and disconnect a client that falls behind? Capping would be a visible protocol change.
